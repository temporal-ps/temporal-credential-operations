Rotation Demo Spec

How the demo for the Temporal Proxy, Vault PKI, and ESO proposal is built and what it proves. It runs the proposal's leaf renewal and client certificate authority (CA) rollover on a local k3d cluster against a real Temporal Cloud Namespace, with the rollover steps implemented as runbook scripts.

Read the proposal first

The approach, its rationale, alternatives, open questions, and evolution path are in spec.html. This page covers only the demo: its topology, components, scripts, demo-only values, and validation. Where the two differ, the proposal governs.

Overview

Executive Summary

A single k3d cluster runs Vault, External Secrets Operator (ESO), two Temporal Proxy deployments, Prometheus, Grafana, and a steady stream of Temporal traffic through the proxies to a real Temporal Cloud Namespace. It starts from a manually generated CA, migrates to a Vault issuer, renews leaves continuously, and runs a full CA rollover, including a deliberately broken proxy that the retirement gate catches. The rollover steps are implemented as runbook scripts, one of the execution options in the proposal.

Scope

  • In scope: leaf renewal through ESO, the rollover scripts, the retirement gate, the migration from a manually generated CA to a Vault issuer, and dashboards and alerts.
  • Out of scope: a command-line tool or RotateCredential Workflow, multi-cluster and multi-region topologies, Vault high availability, production Vault and Kubernetes authorization models, payload encryption, and Temporal Proxy listener TLS.

Goals & Success Criteria

Primary Goals

  • Show leaf renewal with no human action, no restart, and no Temporal Cloud change.
  • Script a CA rollover whose every step verifies its own result and whose retire step cannot run before every proxy has moved to the new issuer.
  • Make each stage of a rotation visible on a dashboard while traffic flows.

Acceptance Criteria

  • A client inside the cluster reaches the Temporal Cloud Namespace only through the proxy, addressed by its Kubernetes Service DNS name, with no Temporal Cloud credentials of its own.
  • The proxy loads each ESO-delivered leaf without a restart; the dashboard shows the leaf expiry advance and reload success at every refresh.
  • Traffic shows no failed calls attributable to TLS across at least three consecutive renewals.
  • The rollover scripts run in order to completion; at the end the Namespace trusts only the new Vault issuer.
  • With one proxy's ExternalSecret deliberately broken, the retire script exits non-zero, names the stale proxy, and changes nothing.
  • Every script can be re-run after success or mid-way failure without a duplicate or destructive change.
  • The Temporal Cloud CA trust set is never written with fewer CAs than at Snapshot, except by the retire script.
  • No CA private key generated by the demo leaves Vault; no secret value appears in committed files, script output, or logs.

Starting Point

The demo's starting point mirrors the current state described in the proposal: a bootstrap CA generated outside Vault, supplied by the person running the demo, and presented by the proxy from a manually created Kubernetes Secret. The proxy is already in place at the start, so the first rollover is the migration to a Vault issuer.

Technical Approach

Design decisions

DecisionRationaleAlternative considered
ESO talks to a real Vault (dev mode) in the cluster The rotation depends on ESO getting a newly signed leaf from pki/issue at every refresh, and on the issuer switch changing what Vault signs. Dev-mode Vault is one Helm install, so the real backend costs about as much as a stub. ESO's fake provider: returns a fixed value, so leaves never change and the gate is meaningless. An AWS emulator behind ESO's AWS provider: nothing in this path calls AWS, and an emulator does not evaluate IAM policies.
Demonstrate the rollover as runbook scripts Each step, precondition, and verification is explicit and can be run and observed on its own. The step contracts carry over to the other execution options. Demonstrate a command-line tool or a RotateCredential Workflow. Their design depends on requirements not yet known.
A Temporal Cloud Namespace dedicated to the demo The scripts own its accepted CA list, so the demo runs every step including retiring the bootstrap CA, and a later run starts again by re-adding it. Anyone can run the demo after cloning the repository and filling in .env.local. A shared Namespace where scripts remove only CAs they added. The bootstrap CA could never be retired, so the demo would stop short of the step that matters most.
Persist rollover state in a ConfigMap Scripts are resumable across shells and operators. The switch time recorded there drives the gate. Local state file. Lost when another operator picks up the rollover.
tcld namespace accepted-client-ca for trust changes It wraps the Ops API, authenticates with an API key, and has list, add, remove (by fingerprint), --request-id, and --resource-version, which give idempotency and optimistic concurrency without custom API code. Direct Ops API calls with curl. Same capability, more script code to review.
Disable the old issuer rather than delete it Setting the issuer's usage to exclude issuing-certificates stops signing but keeps the certificate readable for audit and rollback. Delete the issuer. Irreversible; nothing gained.
One k3d cluster, two client namespaces, a proxy in each Two independent proxies, one serving Workers and one serving Callers, are enough to show a partial failure blocking retirement. One cluster keeps setup to minutes. Two clusters, matching Acme's Worker and Caller separation. Deferred; the gate logic does not change.
Start traffic with the Temporal CLI, add a sample Workflow second A CLI loop through the proxy proves the TLS path and metrics with no application code. A Workflow then proves running executions survive rotations. Build the Workflow first. More code before the first rotation can be observed.
Build Temporal Proxy from its main branch TLS hot reload and its metrics are not in a tagged release yet (latest v1.0.1). Use v1.0.1 and restart on every renewal. Defeats the point of the demo.
Short lifetimes in the demo Leaf TTL 5 minutes and ESO refresh every minute let a routine rollover, with no forced refresh, finish in about 6 minutes. The values live in demo-settings.env and apply-settings.sh applies changes to a running demo without restarting it. Production-like values (days). Nothing visible during a demo. A 10-minute refresh with 30-minute leaves: a routine rollover takes over 15 minutes.

Demo topology

Components

Local inputs (never committed)

InputSourceUsed by
TEMPORAL_DEMO_NAMESPACE_ADDRESS.env.localProxy upstream hostPort (<namespace>.<account>.tmprl.cloud:7233); the Namespace ID is derived from it for tcld.
TEMPORAL_CLOUD_OPS_API_KEY.env.localRunbook scripts only, exported to tcld as TEMPORAL_CLOUD_API_KEY. Belongs to a user or service account with an account-level role (Global Admin). Never placed in the cluster.
TEMPORAL_DEMO_CA_CERT_FILE, TEMPORAL_DEMO_CA_KEY_FILE.env.local (paths to gitignored files)Bootstrap CA certificate and key: the proxy's Secret before migration, and the CA the Namespace accepts at the start.

The repository-root .env.example lists these inputs; a reader copies it to .env.local and fills them in. The proxy is never given an API key: it authenticates with mTLS only, or the demo proves nothing about certificates.

k3d cluster

  • One server node; the locally built proxy image imported with k3d image import.
  • Namespaces: vault, external-secrets, workers, callers, observability.
  • Port-forwards or a load balancer port for Vault, Prometheus, and Grafana so scripts run from the operator's shell.

Vault

  • Dev mode from the official Helm chart (chart 0.34.1, Vault 2.0.4). In-memory state is acceptable: the demo re-bootstraps from scripts. Scripts run the Vault CLI inside the Vault Pod, so the operator needs no local Vault install.
  • PKI mount pki-temporal, issuers named ca-<UTC timestamp> and generated with an internal EC P-256 key.
  • Role temporal-client: ttl and max_ttl from LEAF_TTL (default 5 minutes), client_flag=true, server_flag=false, no_store=true, EC P-256 keys, common names restricted to workers.temporal-proxy and callers.temporal-proxy, issuer_ref set by the switch script. The first run of 02-create-issuer.sh creates the role pointing at the first issuer.
  • Kubernetes auth with one role per client namespace (<ns>-pki), bound to a vault-pki-client service account in that namespace with audience vault, and a policy allowing only update on pki-temporal/issue/temporal-client. ESO requests a short-lived token for that service account; no Pod mounts it.

ESO (per client namespace)

A VaultDynamicSecret generator posting to /pki-temporal/issue/temporal-client, and an ExternalSecret with refreshInterval from ESO_REFRESH_INTERVAL (default 1 minute) templating certificate and private_key into a kubernetes.io/tls Secret named temporal-cloud-leaf. ESO is installed from its Helm chart at a pinned version (2.15.0).

ESO authenticates to the in-cluster Vault with Vault's Kubernetes auth method. No AWS service is emulated and ESO's fake provider is not used; see Design decisions.

Temporal Proxy (per client namespace)

  • Deployment with two replicas, Service temporal-proxy exposing 7233 (gRPC) and 9090 (metrics).
  • Secret temporal-cloud-leaf mounted as a whole volume at /etc/temporal-proxy/cloud; never with subPath.
  • One upstream to $TEMPORAL_DEMO_NAMESPACE_ADDRESS with tls.cert and tls.key only, no credentials block. Clients send the fully qualified Namespace name, so no Namespace rewrite rule is needed.
  • The same upstream serves routing.default and routing.system (Namespace-less system calls).

Traffic

  1. CLI probe (milestone 1). A Deployment in each client namespace running the Temporal CLI in a loop, for example temporal workflow count --address temporal-proxy.<ns>.svc.cluster.local:7233 every two seconds, logging success or the gRPC status. No Temporal Cloud credentials in the Pod.
  2. Sample Workflow (milestone 4). A Worker in workers and a Starter in callers, each pointed at its namespace's proxy. The Workflow runs one Activity and a short timer; the Starter starts one execution per second. Language: Java, using the Temporal Java SDK, as for all Temporal application code in this engagement. This Workflow only generates traffic; it is not the RotateCredential Workflow.

Prometheus and Grafana

  • Prometheus scrapes every proxy Pod through Kubernetes service discovery on label app.kubernetes.io/name=temporal-proxy, keeping the Pod and namespace as labels.
  • Grafana is provisioned with a Prometheus data source and the dashboard in Observability, loaded from a ConfigMap.

Leaf delivery chain

ESO refresh (R), Vault signs, ESO writes the Secret, kubelet syncs the volume (K), proxy polls (P = 1 minute), validates, swaps, and the expiry gauge moves. With the demo defaults each proxy loads a new leaf within about a minute of each refresh, and every proxy is on a new-issuer leaf within R + K + P, about 3 minutes, of a switch.

Timing settings

demo-settings.env holds every demo timing value: the ESO refresh interval, the leaf lifetime, the gate's clock-skew allowance, the issuer lifetime and lead time, and the probe watch after retirement. apply-settings.sh patches the Vault role and each ExternalSecret and re-renders the alert rules, so a change applies to a running demo with only a Prometheus restart; leaves already issued keep their old lifetime. It refuses a refresh interval longer than a third of the leaf lifetime. The leaf lifetime is also how long the demo survives ESO or Vault being unavailable, including the host sleeping.

Rollover sequence

Every script reads .env.local, appends to the rotation-state ConfigMap in the vault namespace, prints what it changed, and ends with its own verification. A script whose precondition fails exits non-zero and changes nothing.

#ScriptActionVerification (exit non-zero if false)
000-preflight.sh Check tools, environment variables, cluster, Vault, and that the Namespace uses mTLS and accepts the current CA (tcld accepted-client-ca list). Every expected proxy reports the expiry gauge; no reload failures in 15 minutes; current role issuer is readable.
101-snapshot.sh Record current issuer, accepted CA fingerprints, expected proxy Pods, and the Namespace resource version. ConfigMap holds all four; the current issuer's fingerprint is among the accepted CAs.
202-create-issuer.sh Generate issuer ca-<timestamp> with an internal key; export its public certificate. Issuer listed in the mount; role still points at the old issuer; no private key in the output.
303-add-trust.sh tcld namespace accepted-client-ca add with the new certificate, using the recorded resource version and a request ID derived from the issuer name. Skip if already present. Accepted set equals Snapshot set plus the new fingerprint.
404-switch.sh Refuse unless step 3 verified. Set the role's issuer_ref to the new issuer; record the switch time. Role reads back the new issuer; switch time recorded.
505-verify.sh Wait until switch + R (no wait after a forced refresh), then evaluate the gate every 15 seconds until it passes or a timeout (default 2R + 5 minutes). Gate passes. On timeout, print each stale proxy and its leaf expiry, and exit non-zero.
606-retire.sh Re-run the gate. Remove the old fingerprint with accepted-client-ca remove. Set the old issuer's usage to read-only,crl-signing. Accepted set equals Snapshot set minus old plus new; the old issuer refuses to sign.
Rrollback.sh Before step 4: remove the new CA from trust. After step 4: set issuer_ref back to the old issuer. Never removes the old CA. Role and accepted set match the state the rollback targets.

Emergency rollover uses the same scripts with a forced ESO refresh between steps 4 and 5: changing the force-sync annotation on each ExternalSecret makes ESO reissue the leaf within seconds (force-refresh.sh).

First run: migration from the manual CA

The first execution moves the proxies from the manually generated CA to Vault. It differs from a routine rollover in two steps:

  1. Bootstrap. bootstrap-manual.sh creates Secret temporal-cloud-leaf-manual in each client namespace from the bootstrap CA certificate and key, and deploys the proxies mounting it. If the Namespace no longer accepts the bootstrap CA (a previous run retired it), the script adds it back and waits until a call succeeds, as in step 3. Traffic flows; this is Acme's current state with a proxy in front.
  2. Snapshot, create issuer, add trust. As steps 1 to 3. The manual CA is recorded as "old". Step 3 also proves the Namespace accepts the new issuer by completing a call with a 5-minute test leaf, so the switch never depends on CA propagation timing.
  3. Switch (migration form). Instead of changing issuer_ref, migrate-switch.sh applies the ESO resources, waits until each temporal-cloud-leaf Secret holds a leaf signed by the new issuer, then repoints each proxy Deployment at it. This is the only Pod restart in the design. A new Pod that cannot connect never becomes Ready, so a rejected leaf stalls the rollout with the old Pods still serving.
  4. Verify. As step 5.
  5. Retire. As step 6: after the gate passes, the bootstrap CA is removed from the Namespace like any other old CA.

Retirement gate

The gate passes only when all three hold:

# 1. Every expected proxy Pod is reporting (count must equal the Snapshot count)
count(tmprl_proxy_tls_cert_expiry_timestamp_seconds{file="cert"})

# 2. No proxy is on a leaf issued before the switch (must be empty)
tmprl_proxy_tls_cert_expiry_timestamp_seconds{file="cert"}
  < ($switch_time + $leaf_ttl - $skew)

# 3. No recent reload failures (must be empty)
increase(tmprl_proxy_tls_reloads_total{result="failure"}[15m]) > 0

The skew is a clock-skew allowance between Vault and the clock that records the switch. A leaf issued within skew before the switch would count as new, so the skew must stay far below R: the demo uses 5 seconds on one host clock; production uses its measured clock-skew bound.

Pods restarted during the rollover change the expected set. The script compares against the current ready replica count of each proxy Deployment, not Pod names. Prometheus keeps returning a terminated Pod's series for several minutes, so the gate evaluates only series whose Pod Kubernetes currently reports as Ready (observed during the migration rollout: 8 series for 4 Ready Pods).

The gate is cross-checked once, independent of metrics: for one proxy Pod per namespace, read the mounted certificate and print its issuer, serial, and NotAfter with openssl x509. The issuer must be the new ca-<timestamp> and the NotAfter must match the gauge.

Alerts

Prometheus alert rules, rendered from rules.yml.tmpl with the thresholds derived from the timing settings:

# Leaf renewal stalled: two refreshes missed
(tmprl_proxy_tls_cert_expiry_timestamp_seconds{file="cert"} - time()) < ($leaf_ttl - 2 * $refresh_interval)

# Proxy rejected new material
increase(tmprl_proxy_tls_reloads_total{result="failure"}[10m]) > 0

# A proxy stopped reporting (per namespace, against its replica count)
count by (namespace) (tmprl_proxy_tls_cert_expiry_timestamp_seconds{file="cert"}) < $replicas

# Calls to Temporal Cloud failing at the proxy
increase(tmprl_proxy_router_forwarding_errors_total[5m]) > 0

Issuer expiry is not a proxy metric. The proxy's file="ca" series tracks the CA used to verify Temporal Cloud's server certificate. A small script, check-issuer-expiry.sh, reads the current issuer's NotAfter from Vault and fails when it is closer than the rollover lead time; production would run it on a schedule or replace it with a Vault-side metric.

Invariants

  • The only CA a script removes from the Namespace is the Snapshot's old CA, by 06-retire.sh, after the gate passes. The demo Namespace is dedicated to the demo, so the bootstrap CA is removable on the same terms.
  • 04-switch.sh refuses to run unless the new CA is verified in the Namespace; 06-retire.sh refuses to run unless the gate passes.
  • Every Temporal Cloud write uses the recorded resource version, so a concurrent change makes the script fail instead of overwriting.
  • The Ops API key exists only in the operator's shell during the procedure.
  • ESO's Vault policy can issue leaves only.
  • No script prints a private key or secret value.

Demo

  • Lives at: demos/credentials-management/temporal-proxy-vault-eso/
  • Scenario: bring up the cluster with the manual CA; watch traffic through the proxies; migrate to Vault; watch three renewals; run a rollover; break one namespace's ExternalSecret and watch the retire script refuse; fix it and retire.

Implementation Strategy

  1. Proxy path. k3d cluster, locally built proxy image, bootstrap Secret from the manual CA, CLI probes in both namespaces, Prometheus and Grafana with the expiry and reload panels. Replace the bootstrap Secret by hand once to see hot reload. Done when probes succeed through Service DNS and the gauge moves after the manual replacement.
  2. Vault PKI and ESO. Vault dev mode, PKI mount, role, Kubernetes auth, ESO, and the migration run. Done when three consecutive renewals reload with no probe errors.
  3. Rollover scripts. Steps 0 to 6, rollback, the ExternalSecret failure injection, dashboard annotations, alert rules, the timing settings, and demo-rollover.sh, which runs steps 0 to 6 in one command. Done when the failure case exits non-zero and the repaired run completes.
  4. Sample Workflow. Worker and Starter replace the probes. Done when executions complete continuously across a full rollover.
  5. Runbook text. Written from the scripts' actual output.

Validation Strategy

Runbook Validation

  • Every script runs as written against the demo cluster and a real Temporal Cloud Namespace.
  • Every script is re-run after success and after an injected mid-way failure.
  • Output is reviewed for secret values.

Demo Validation

  • Runs from a clean machine with only the documented local inputs.
  • The dashboard shows each stage listed in the scenario.
  • The Namespace's accepted CA set at the end matches the invariants.

Implementation Notes

  • Temporal Proxy refuses to start when its configured client certificate has expired, so an expired leaf in the Secret turns a proxy restart into a crash loop until ESO writes a valid one.
  • The bootstrap certificate is a CA certificate (CA:TRUE), not a leaf. Once trusted by the Namespace it can be presented directly, but rotate-manual-leaf.sh signs a proper client leaf with it instead.
  • Temporal Proxy requires tls.ca on an upstream whenever a client certificate is set; the demo uses the image's system CA bundle.
  • Temporal Proxy exits at startup when its upstream connection does not become ready, so a rejected credential shows up as a crash loop, not a running proxy with failing calls.
  • tcld reads its API key from TEMPORAL_CLOUD_API_KEY; scripts export it from TEMPORAL_CLOUD_OPS_API_KEY for the process only.
