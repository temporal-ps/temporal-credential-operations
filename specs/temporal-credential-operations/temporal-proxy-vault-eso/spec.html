Proxy, Vault, and ESO Rotation

A proposed way to operate Temporal Cloud client credentials at Acme: Vault PKI signs short-lived client certificates, External Secrets Operator (ESO) delivers them, and Temporal Proxy is the only process that presents them to Temporal Cloud. Leaf renewal becomes routine and unattended; a client certificate authority (CA) rollover becomes a short, verified procedure whose riskiest step is gated on metrics. Written for the operations, infrastructure, and Kubernetes teams to evaluate.

Summary

Today every certificate renewal is also a CA change, a Temporal Cloud trust change, and a coordinated restart of Worker and Caller Deployments, and the decision to remove the old CA rests on judgment. This proposal separates the two things that change at different rates:

  • Leaves are short-lived and renewed continuously by ESO from a Vault PKI issuer. Temporal Proxy reloads each new leaf without a restart. Temporal Cloud trust does not change.
  • The CA is long-lived and lives only in Vault. Rolling it over is a fixed sequence of verified steps. The old CA is removed from Temporal Cloud only when every proxy reports, through its own metrics, that it presents a leaf from the new CA.

Applications stop holding Temporal Cloud credentials at all. They connect to the proxy by its Kubernetes Service name; the proxy holds the leaf and makes it observable.

What this asks of each team
  • Infrastructure team (Vault): a PKI mount and role for Temporal client leaves, and a Kubernetes auth role per client cluster limited to issuing them.
  • Kubernetes team: a Temporal Proxy Deployment and ESO resources in each client namespace, and metrics collection from every proxy.
  • Fulfillment team (Temporal applications): point Workers and Callers at the proxy's Service address and remove their client certificate configuration.
  • Whoever owns Temporal Cloud Namespace configuration: let the rollover change accepted client CAs, which today Terraform Enterprise manages (see Open Questions).

Current State

  1. Generate. A new CA and client certificate are created together, outside Vault PKI, shortly before the current ones expire.
  2. Add trust. The fulfillment team applies a Terraform Enterprise change that adds the new CA next to the old one.
  3. Distribute. An operator replaces the certificate and key in a Vault secret, then restarts or redeploys Workers.
  4. Check. An operator watches Pod health and error dashboards.
  5. Retire. The fulfillment team removes the old CA in Terraform Enterprise and checks the Temporal Cloud UI.

Pain points

  • Every renewal is also a CA change and a Temporal Cloud trust change.
  • The CA private key exists outside Vault and passes through people.
  • New material takes effect only when application Pods restart, across separate Worker and Caller pipelines.
  • Nothing shows which certificate a running process presents. Old-CA removal is a judgment call, and a client the procedure missed fails only after old trust is removed.
  • Warning of an approaching expiry arrives by email: it reaches individual inboxes rather than on-call, and says nothing about which processes still present the certificate.

Capabilities already in place

Discovery reported that Acme already runs a shared, centrally managed Vault with the PKI secrets engine enabled, Vault Kubernetes authentication, and ESO. The proposal uses those rather than introducing new secret infrastructure. The new component is Temporal Proxy.

Two lifecycles

Leaf renewal: continuous

ESO asks Vault for a new leaf every refresh interval R. Kubernetes syncs the Secret volume (K), the proxy polls it (P), validates the new pair, and swaps it in. Nobody acts; Temporal Cloud trust does not change; no Pod restarts.

CA rollover: once per CA lifetime

Create a new issuer, add it to Temporal Cloud trust, switch Vault to sign with it, wait until every proxy presents a new-issuer leaf, then remove the old CA. Emergency rollover is the same sequence with a forced ESO refresh after the switch.

Standing checks: always

Alerts fire on a leaf that stops renewing, a proxy that rejects new material, a proxy that stops reporting, calls failing at the proxy, and an issuer approaching its own expiry.

The timing relationships that govern both lifecycles:

  • Every proxy presents a new-issuer leaf within about R + K + P of a switch. That bounds how long the old CA must stay trusted.
  • A leaf of lifetime L refreshed every R survives an ESO or Vault outage of about L − R. After that, proxies present expired leaves and Temporal Cloud rejects them.
  • R should be no more than a third of L, so two missed refreshes alert before the leaf expires.

What Temporal Proxy makes observable

Temporal Proxy adds a component to the call path. In exchange, it is the only process that holds a Temporal Cloud client certificate, and it reports which certificate it loaded and whether loading succeeded. That turns questions answered today by email or judgment into alerts routed to on-call.

QuestionTodayWith Temporal Proxy
Is a certificate close to expiry? Email to individuals, per CA, with no link to the processes using it. Alert on each proxy's loaded-leaf NotAfter, firing when renewal stalls, long before expiry.
Did new material take effect? Known only after Pods restart and connect. Reload counter by result. A failed reload alerts while the proxy keeps serving its previous leaf.
Is any client missing from the rollout? Found when it fails after old trust is removed. Alert when fewer proxies report than expected.
Is every client on the new CA? Operator judgment. Retirement gate query across every proxy.
Is Temporal Cloud rejecting connections? Application errors and Pod health. Forwarding errors by reason on the proxy, separate from application errors.

Rollover sequence

Each step has a precondition and a verification. A step whose precondition fails changes nothing; a step whose verification fails stops the rollover. Every step is idempotent, so a rollover resumes by re-running the step that stopped. These step contracts are the same whichever execution option runs them.

#StepActionVerification
0Preflight Check that each Namespace in scope uses mTLS and accepts the current CA, and that every proxy is healthy. Every expected proxy reports a loaded leaf; no recent reload failures; no loaded leaf close to expiry.
1Snapshot Record the current issuer, each Namespace's accepted CA fingerprints and resource version, and the expected proxy count. The current issuer is among each Namespace's accepted CAs.
2Create issuer Generate a new issuer in Vault with an internal key; export only its public certificate. Issuer exists; Vault still signs with the old issuer.
3Add trust Add the new CA to each Namespace's accepted client CAs, using the recorded resource version. Accepted set equals Snapshot plus the new CA; a call with a test leaf from the new issuer succeeds.
4Switch Refuse unless step 3 verified. Point the Vault role at the new issuer; record the switch time. Vault signs with the new issuer.
5Verify Evaluate the retirement gate until it passes or times out. Gate passes. On timeout, name each stale proxy.
6Retire Re-evaluate the gate. Remove the old CA from each Namespace; disable signing on the old issuer, keeping it readable. Accepted set equals Snapshot minus old plus new; the old issuer refuses to sign.
RRollback Before step 4: remove the new CA from trust. After step 4: point the role back at the old issuer. Never removes the old CA. Role and accepted set match the state rolled back to.

Retirement gate

The gate passes only when all three hold:

# 1. Every expected proxy Pod is reporting (count must equal the expected count)
count(tmprl_proxy_tls_cert_expiry_timestamp_seconds{file="cert"})

# 2. No proxy is on a leaf issued before the switch (must be empty)
tmprl_proxy_tls_cert_expiry_timestamp_seconds{file="cert"}
  < ($switch_time + $leaf_ttl - $skew)

# 3. No recent reload failures (must be empty)
increase(tmprl_proxy_tls_reloads_total{result="failure"}[15m]) > 0
  • Condition 2 works because Vault leaves have a fixed lifetime: a leaf whose NotAfter is later than switch + L − skew was issued after the switch, so by the new issuer.
  • The skew allowance covers clock difference between Vault and whatever records the switch time. It must stay far below R, or a leaf issued just before the switch passes as new.
  • The expected count comes from the current ready replicas of every proxy Deployment, and the gate evaluates only series from Pods currently Ready. Metrics systems keep returning a terminated Pod's series for several minutes.
  • The gate is only as complete as the proxy inventory. A client that presents a certificate from the old CA without going through a proxy is invisible to it; see Risks.

Migration from today

The first rollover moves clients from today's manually generated CA to a Vault issuer. It is the only step in the design that restarts Pods.

  1. Introduce the proxy with today's certificate. Deploy the proxy in each client namespace mounting the existing certificate and key, then repoint Workers and Callers at it. Nothing about trust changes.
  2. Snapshot, create issuer, add trust. As steps 1 to 3. Today's CA is recorded as the old CA.
  3. Switch (migration form). Apply the ESO resources, wait until each Secret holds a leaf from the new issuer, then roll each proxy Deployment onto that Secret. A new proxy Pod that cannot connect never becomes Ready, so a rejected leaf stalls the rollout while the old Pods keep serving.
  4. Verify and retire. As steps 5 and 6. Today's CA is removed like any old CA.

Security model

  • CA private keys are generated inside Vault and never exported. Nothing outside Vault can sign a leaf.
  • ESO's Vault policy allows only issuing leaves from one role. The role restricts common names, sets client-auth only, and does not store issued leaves.
  • A leaf's private key exists only in its Kubernetes Secret and the proxy that mounts it. Applications have none.
  • The Temporal Cloud Ops API key is the most privileged credential involved: it can change any Namespace's trust. Where it lives depends on the execution option and is an open question.
  • Only step 6 removes trust, only for the CA recorded at Snapshot, and only after the gate passes. Every trust write uses the recorded resource version, so a concurrent change fails the step instead of being overwritten.
  • The old issuer is disabled rather than deleted, so its certificate stays available for audit and rollback.

Design Decisions & Alternatives

DecisionRationaleAlternative considered
Temporal Proxy holds the client credential One process type per cluster presents, reloads, and reports the certificate. Applications need no TLS reload logic and no restarts; the gate has one metric to query. Each Worker and Caller loads and reloads its own certificate. Every application must implement reload correctly, and nothing reports which certificate each process presents, so retirement stays a judgment call.
Short-lived leaves from a long-lived Vault issuer Renewal no longer touches Temporal Cloud trust or people. The CA changes only at its own, much longer interval. Keep generating a new CA per renewal (today). Every renewal stays a trust change and a coordinated restart.
ESO delivers leaves Already running at Acme. A Vault generator issues a new leaf on each refresh into an ordinary Kubernetes Secret; the proxy needs no Vault integration. Vault Agent sidecar or Vault Secrets Operator: viable, but adds a component per Pod or a new operator. cert-manager with a Vault issuer: also viable; not reported as in use.
Retire the old CA on a metrics gate Retirement is the only step that can cause an outage; the gate makes it depend on what every proxy reports it loaded. Retire after a fixed wait. Silent on a proxy that never renewed.
Change trust through the Temporal Cloud Ops API Supports list, add, and remove by fingerprint with request IDs and resource versions, giving idempotency and optimistic concurrency per step. Change trust through Terraform Enterprise, as today. Keeps one source of truth but puts a plan and apply inside the rollover; see Open Questions.
Disable the old issuer, do not delete it Stops signing, keeps the certificate readable for audit and rollback. Delete the issuer. Irreversible; nothing gained.

Rollover Execution Options

Once leaf renewal is automatic, nothing day to day needs orchestration. The rollover sequence can be executed in several ways. Each option runs the same step contracts; they differ in who runs the steps, how durably, and across how many Temporal Cloud Namespaces.

OptionShapeDurabilitySuitsCosts
Runbook scripts An operator runs one script per step, per Namespace, reading each result before the next. Rollover state in a Kubernetes ConfigMap; every step is idempotent and resumable by re-running it. Waits are attended. Few Namespaces and infrequent rollovers. Operator time per Namespace. The Ops API key is held in the operator's shell for the rollover.
Command-line tool One command runs the steps in order for a list of Namespaces, stopping at the gate or on any failed verification. Same state record per Namespace; resumes by re-running. A closed terminal ends the run, and long waits occupy the operator's session. Tens of Namespaces rolled over in an attended session. A tool to build, version, and distribute. No Worker or new owning team.
RotateCredential Workflow Each step is an Activity; the gate is a durable wait. One Workflow per rollover fans out across N Namespaces. It supervises only credential material: the Vault issuer, each Namespace's accepted CAs, and the leaf each proxy reports it loaded. Durable across hours or days of waiting, process restarts, and operator handoffs. Retries, history, and approvals (Signals or Updates) come from Temporal. Many Namespaces, frequent or scheduled rollovers, unattended runs. A Worker, an owning team and on-call, and a long-lived, secured holder of the Ops API key.

Because Temporal Proxy is the only holder of Temporal Cloud client credentials, no option selects, restarts, or inspects Worker and Caller Deployments. The requirement with the largest effect on the choice is CA topology: one CA shared across Namespaces makes a rollover one issuer switch, N trust changes, and one gate across every proxy; one CA per Namespace or per trust domain makes it N independent rollovers. The demo implements the runbook scripts; this proposal does not recommend an option until the open questions are answered.

Risks & Failure Modes

RiskImpactLikelihoodMitigation
A client presents a certificate from the old CA without going through a proxy (for example, Callers in a separate cluster not yet migrated)HighMediumInventory every client of every Namespace before the first retirement. The gate only sees proxies; removing the old CA breaks any client it does not see.
The proxy becomes a single point of failure for Temporal trafficHighLowMultiple replicas, a PodDisruptionBudget, and the proxy-missing and forwarding-error alerts.
ESO or Vault unavailable longer than L − RHighLowSize L to exceed Vault's recovery objective. The renewal-stalled alert fires after two missed refreshes. A proxy restarted with an expired leaf refuses to start until ESO writes a valid one.
Terraform restores a CA the rollover removed, or removes one it addedHighMediumDecide who owns accepted client CAs before the first rollover; see Open Questions.
TLS hot reload is not in a tagged Temporal Proxy releaseMediumHigh (today)The demo builds from a pinned main-branch commit. Production adoption waits for a release that includes hot reload and its metrics, or accepts a pinned build.
Metrics from Worker and Caller clusters are not queryable in one placeMediumMediumThe gate needs a view of every proxy. Either centralize proxy metrics or evaluate the gate per cluster and combine the results.
Ops API key misuse or leakHighLowHold it only where the chosen execution option needs it, for as short a time as that option allows; use a service account with the narrowest role that can change accepted CAs.

Open Questions

Needed before production adoption

  • OPEN QUESTION: Client inventory. Which Workers and Callers, in which clusters, present certificates signed by the current CA? Do Callers share the Workers' CA?
  • OPEN QUESTION: Ownership of accepted client CAs. Does Terraform Enterprise stop managing that field (for example with ignore_changes) so the rollover owns it, or does the rollover drive Terraform?
  • OPEN QUESTION: Vault PKI placement. Which mount, role, and Kubernetes auth roles the infrastructure team will provide, and who approves issuer creation and switch.
  • OPEN QUESTION: Where proxy metrics land, and whether one query can see every proxy across Worker and Caller clusters.
  • OPEN QUESTION: Proxy placement. One proxy per client namespace, per cluster, or per Temporal Cloud Namespace, given that clusters and Namespaces are not one to one.

Needed before choosing an execution option

  • OPEN QUESTION: CA topology. One client CA shared by every Namespace, one per Namespace, or one per trust domain (for example per environment or per region)?
  • OPEN QUESTION: Acme security team requirements: CA and leaf lifetimes, rollover frequency, separation between Namespaces or environments, who may approve trust changes, and where the Ops API key may be held.
  • OPEN QUESTION: Number of Temporal Cloud Namespaces in scope, now and planned.
